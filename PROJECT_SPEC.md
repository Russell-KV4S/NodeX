## 1. Project overview & objective

NodeX is a standalone AllStarLink (ASL) node for **Windows, Linux, macOS, Android and iOS**, built with **.NET 10** and **Avalonia UI**. It is a genuine peer node on the ASL network (IAX2 over UDP 4569; registration over IAX2 from the call socket, HTTPS as fallback, see §5.1a) — **not** a WebTransceiver or `iaxrpt` guest client — and it needs **no Asterisk and no radio hardware** ("radio-less"). Audio comes from the device microphone/speaker or a paired Bluetooth speaker-mic/headset whose hardware button acts as push-to-talk (PTT).

Primary use case: a **portable node on a phone or laptop** that registers with AllStarLink, links *outbound* to other nodes, and stays connected while the screen is off and while the device moves between Wi-Fi and cellular.

### Key features (headline list; keep in step with the README "Features" section)

1. **Always on, in the background.** On Android a foreground service keeps links alive with the screen off or the app backgrounded, and the node retries until the *user* disconnects (§4.6), surviving Wi-Fi/cellular handoff, dropped calls and dead spots. Nothing but the user's own Mute or Disconnect ends audio. (Owner-field-reported for 1 h+ screen-off and handoff; see §2.)
2. **Multiple nodes at once.** Up to 8 simultaneous outbound links, live mixed audio, per-node mute/disconnect, one explicit transmit node, no cross-linking between nodes (§4.5 / §2).
3. **Android Auto.** Native car media app: browse links and favourites, focus/mute/disconnect, optional car-radio audio mix; the full GitHub edition adds optional Talk-button / steering-wheel PTT, Play edition is listen-only.
4. **Audio Replay and WAV sharing.** Replay the last received clip or browse and filter received and transmitted clips, multi-select clips to combine chronologically into one standalone WAV file, or delete clips individually/in batch. Both Android editions share WAV files through the Android share sheet; Desktop reveals the WAV in the file manager. Saving is on by default, with a configurable clip-count limit (25/50/100/200 clips), keeps clips strictly on the local device until shared, and stops replay when PTT keys (§4.8).

Design stance: **outbound-linking only.** Carrier-grade NAT blocks unsolicited inbound IAX2 on cellular, so NodeX dials out and ignores inbound link attempts (an inbound listener would only be possible over a VPN overlay such as WireGuard/Tailscale; not implemented).

### 3.3 Build output location — IMPORTANT
The repo lives in a **OneDrive** folder. OneDrive pins `bin`/`obj` directories as read-only cloud-file reparse points, which made Android/iOS builds fail intermittently with "Access to the path … is denied" (`MSB3231`, `XARDF7024`) — *not* code errors. `Directory.Build.props` therefore redirects all intermediate/output paths to **`%LOCALAPPDATA%\NodeX\build\{obj,bin}\<ProjectName>\`** (override with the `NODEX_BUILD_ROOT` environment variable). Consequences:
- Built binaries are **not** under the project folders. Desktop exe: `%LOCALAPPDATA%\NodeX\build\bin\NodeX.UI.Desktop\Debug\net10.0\NodeX.UI.Desktop.exe`.
- If you ever see lock errors again: `attrib -R -P +U "<dir>\*" /S /D` then delete the directory.
- Do not create `bin`/`obj` folders inside the repo.

The app reads the public feed without a GitHub token.

**Release pipeline:** `.github/workflows/release.yml` runs on version tags or manual dispatch for an existing tag. The tag must match `NodeXVersion` in `Directory.Build.props`, which also sets the increasing `NodeXVersionCode` for Android. Core and headless UI tests gate all eight packages. The Android job uses the existing key from Actions secrets to sign the full APK and Play AAB, and verifies the AAB with `jarsigner`. Desktop packages are self-contained for Windows x64/ARM64, Linux x64/ARM64 and macOS Apple Silicon/Intel. The publish job adds the APK update manifest and SHA-256 checksums for the release files, uploads everything to a draft, then publishes it. Increment both versions for a new release and preserve published assets. Apple packages use ad-hoc signing. Hardware validation remains outstanding on Linux/macOS and for Android update installation.

**Stable assets** are `NodeX-android.apk`, `NodeX-android-play.aab`, `NodeX-win-x64.zip`, `NodeX-win-arm64.zip`, `NodeX-linux-x64.tar.gz`, `NodeX-linux-arm64.tar.gz`, `NodeX-osx-arm64.zip` and `NodeX-osx-x64.zip`. Packages retain NodeX's license and desktop third-party notices, including SimpleBLE's separate terms. The bundled SimpleBLE backend requires macOS 15+ on Apple Silicon. Audio and BLE require separate platform testing.

**Android updater, first implementation:** full Android only. A foreground open/resume checks at most once per day per running process; Settings → App updates also permits an explicit check. The phone displays an available-update notice linking to Settings. No download or install starts automatically; checks neither dial nor disconnect nodes. The app reads only the fixed repository's latest stable release, ignores drafts/prereleases, and requires a complete manifest/APK pair. The versionCode must exceed the installed code (same/older versions are never offered). The manifest's version must match the tag, and the manifest must identify `com.kv4s.nodex` and the fixed APK asset. Size is bounded to 512 MiB, JSON to 1 MiB, and the APK's declared size and SHA-256 must match before a private-cache `.part` becomes an installable file. Failures/cancellation remove partial downloads. Manual downloads can be cancelled and have a 15-minute timeout; checks time out after 30 seconds.

**Installation:** refuse while any node is connecting/linked/reconnecting or Android Auto is active; check again after downloading. When active links (and not Android Auto) block installation, Settings → App updates shows an inline prompt with **Disconnect & update** (disconnects all linked nodes immediately and proceeds to download/install) and **Cancel** (leaves links untouched so the user can disconnect manually later). When Android Auto is active, no software disconnect prompt is shown; the user must leave Android Auto first. Validate APK package ID, versionCode and signing certificate against the installed full edition; rehash the cached file before launching installation. Share only the `cache/updates/` subtree using a non-exported FileProvider with temporary read permission. Android 8+ requires the user's “Allow from this source” permission; after granting it, return to NodeX and tap install again. Android's package installer always requests final confirmation. Same-key in-place updates preserve settings and Keystore-protected passwords. Do not rotate the signing key in this initial implementation. No silent updates or automatic app restart. Play builds compile out the updater entry point/provider and omit `REQUEST_INSTALL_PACKAGES`; iOS/desktop have no self-installer in this first phase.

**Update feed:** the app has no GitHub authentication and relies on the public releases feed, now anonymous-readable (repository made public 2026-11-12; the in-app check/download flow has not yet been re-tested against it). A 404 reports that the repository may be private or have no release; it must not falsely say “up to date.” Switching Play ↔ sideload may require uninstalling because of different signing certificates: export settings first and be prepared to re-enter the node password. ### 4.2 `Iax2Session` (Core/Protocol) — one call over UDP
Single-use: it owns a socket and four background loops (receive, keep-alive, retransmit, link-list). **Create a new session per call; never reconnect a used one.**
- **Handshake:** first `NEW` carries an *empty* CALLTOKEN IE; on a `CALLTOKEN` reply it clears pending frames, resets sequence numbers/remote call number and re-sends `NEW` with the token; `ACCEPT` → `Connected`. `AUTHREQ`/MD5 auth is implemented (not needed for node links).
- **Reliability (RFC 5456 §7):** every full frame except ACK/INVAL/TXCNT/TXACC/VNAK/CALLTOKEN is sequenced (8-bit, wraps) and queued until the peer's ISeqno acknowledges it; retransmitted with the R bit on a timer (initial `InitialRetransmitTimeout` 1 s until an RTT is measured, then 2×RTT clamped 100 ms–10 s; doubles per retry, cap 10 s); after `MaxRetransmits` (4) the call is declared lost. Inbound: out-of-order (future) frames are ignored and answered with **VNAK**; duplicates are re-ACKed and not re-processed; ACKs are never ACKed.
- **Keep-alive:** `PING` every `KeepAliveInterval` (15 s); the peer's `PONG` echoes our timestamp → RTT (`RoundTripTime`, `RoundTripTimeUpdated`). **Watchdog:** any valid inbound packet resets a counter; `MaxMissedKeepAlives` (3) silent intervals → link lost. `POKE`/`PING` from the peer are answered with `PONG`; `LAGRQ` with `LAGRP` (timestamp echoed).
- **Validation:** only packets from the dialled endpoint are accepted; frames must carry our call number as destination and the peer's call number as source; mini frames must match the established peer.
- **Audio frames:** the first voice frame of each transmission (and every 16-bit timestamp wrap) is sent as a *full* Voice frame (subclass = codec 0x04 µ-law); subsequent frames are 4-byte-header **mini frames** (low 16 bits of the ms timestamp).
- **Disconnect reason:** `DisconnectReason` ∈ {None, LocalRequest, RemoteHangup, RemoteRejected, RemoteBusy, LinkLost}, set *before* `StateChanged(Disconnected)`. Which reasons are redialled is decided by `NodeRuntime` per §4.6 (lost links, early hang-ups, hang-ups without `!!DISCONNECT!!`, never-answered/busy dials); `RemoteRejected` is never redialled.
- **Threading rule:** events (`StateChanged`, `RemoteKeyedChanged`, `VoiceFrameReceived`, …) fire on the **receive/keep-alive/retransmit threads**. Never dispose the session from inside a handler (it used to deadlock; `DisposeAsync` now bounds its waits at 2 s, but handlers should still hand off to another task, as `NodeRuntime` does).
- **Robustness rules (2026-11-11, all unit-tested):**
  - *No loop may die from one bad event.* The receive loop survives a socket error (Windows reports ICMP "port unreachable" as a receive failure; that is switched off with `SIO_UDP_CONNRESET` and tolerated anyway; only about 2 s of nothing but errors ends the call as `LinkLost`) and a frame whose handling throws (reported as "IAX2 frame handling error", the frame is lost, the call is not). The keep-alive, link-list and retransmit loops treat a send that fails as a lost packet instead of ending.
  - *Disconnected is final.* State changes go through one lock; once a dialled session is `Disconnected` nothing brings it back (a late `ACCEPT`/`ANSWER` is ignored), the reason is the first one recorded and `StateChanged(Disconnected)` is raised once. A used session refuses `ConnectAsync`. `ACCEPT`, `ANSWER` and `AUTHREQ` only act while the call is being set up; a `CALLTOKEN` frame is only honoured before the peer has answered (it bypasses the call-number check, so mid-call it used to reset the sequence numbers and send a second `NEW`). While hanging up or after the end, inbound frames are still acknowledged but nothing in them is acted on.
  - *Sequence numbers have one owner:* every read and change of `OSeqno`/`ISeqno` (sequenced frames, ACK/VNAK headers, the inbound increment, the call-token reset) happens under `_sendLock`.
  - *Each `StateChanged` listener is called on its own*, so one that throws cannot stop the runtime hearing that a call ended.
  - *HANGUP is delivered, not just sent.* `DisconnectAsync` re-sends HANGUP every 100 ms until the peer acknowledges it (or answers `INVAL`), for at most `HangupAckWait` (300 ms), then closes anyway. `DisposeAsync` hangs up before it stops the loops so the acknowledgment can be seen. `NodeRuntime` sets the wait to zero for links it ends because the network changed, and hangs several links up in parallel.
  - *Authentication:* only the MD5 challenge is answered; see §10.
- **Limitations:** IPv4 only; binds `preferredLocalPort` when specified and free, falling back to an ephemeral UDP port when 0 or in use; G.711 µ-law only; no call transfer; `AST_FRAME_TEXT` (`!NEWKEY1!`, `L <links>`, `T <node> STATUS,…`) is parsed by `AslTextParser` and surfaced on `NodeLink.RemoteLinkedNodes` / `LinkItemViewModel.RemoteLinksText` (see §14).

### 4.3 `NodePttController`
Sources: UI button, Bluetooth, media key, VOX. Modes: **Momentary** (hold) / **Toggle** (tap to start, tap again to stop; UI release ignored; media key always toggles). A **Time-Out Timer** (default 180 s, per-key-up restart) force-unkeys with source `External`. Sends `AST_CONTROL_KEY` (0x0C) / `UNKEY` (0x0D) through the session; `SetPttStateAsync` is idempotent and thread-safe. Disposal unkeys. **`HandleButtonAsync(pressed, source)` (2026-11-06)** is the one place a physical button follows the PTT mode (Momentary: hold to key; Toggle: each press flips, release ignored); Bluetooth and the mapped phone button both use it. **`Policy` (`TransmitPolicy`, 2026-11-06):** keying is refused (with a `WarningLogged` explaining why) while transmit is blocked, and an active key is released if it becomes blocked; unkeying is never blocked. `TransmitPolicy` (owned by `NodeRuntime.Transmit`) blocks when `ListenOnly` (from settings) or `MicrophoneAllowed` is false (set by a platform head; Android does this from `RECORD_AUDIO`). **Listening never depends on it**: with the mic denied the app still connects and plays received audio (the mic is opened only while keyed, so it is never opened). **`TransmitEnabled` / `ListenOnlyReason` (2026-11-06):** a per-link gate, default true. With several nodes linked `NodeRuntime` sets it true only on the transmit node's link; keying a listen-only link is refused with a `WarningLogged` ("Node N is listen-only. Choose it as the transmit node…"), and clearing it on a keyed link unkeys it. It is independent of `Policy`. **Connected-only and serialised (2026-11-11):** a key is refused (with a `WarningLogged`) unless the session is `Connected`, and key/unkey requests run one at a time so the controller and the session can never disagree about being keyed; see the change log.

### 4.4 Audio pipeline (Core/Audio)
- **Format:** 8000 Hz, 16-bit, mono, 20 ms frames (160 samples) everywhere in Core (`AudioFormat`).
- **`IAudioDeviceService`** (implemented per platform): `StartCapture(Action<ReadOnlyMemory<short>>)`, `StopCapture`, `StartPlayback`, `StopPlayback`, `EnqueuePlaybackPcm`, `BufferedPlayback`, `ErrorOccurred`. Capture callbacks arrive on the driver's audio thread with arbitrary block sizes.
- **`NodeAudioEngine`:** capture → `PcmFramer` (exact 160-sample frames) → mic gain → level meter → (only while PTT keyed) µ-law → bounded drop-oldest queue (8) → `Session.SendAudioFrameAsync`. Receive: `VoiceFrameReceived` → µ-law decode → `JitterBuffer` → 20 ms playout clock (5 ms timer, catch-up, stall protection) → device. Skips frames if the device backlog exceeds 200 ms. `KeepAudioPipelineAlive` writes zero PCM during silence (**iOS keeps its audio session/background execution alive this way**).
- **Start and stop never interleave (2026-11-12):** `Start`, `StopAsync` and `DisposeAsync` share one lock, and `Start` does nothing after disposal. A call hung up about 100 ms after it was accepted starts its audio on a worker thread while the runtime disposes it; the two used to interleave, which showed on a phone as "Audio could not start: Object reference not set to an instance of an object" and could open the playback device after it had been stopped. The new tests fail with that exact exception on the old code.
- **`JitterBuffer`:** timestamp-keyed (16-bit wrap safe), prime depth 3 frames (60 ms), capacity 25, reorder, drop late/duplicate, conceal up to 3 lost frames by repeating the last frame with halving gain, re-prime after idle; thread-safe.
- **`PcmResampler`:** streaming area-averaging resampler to 8 kHz (used on iOS capture; hardware is usually 44.1/48 kHz). **`AudioLevelMeter`:** RMS/peak with attack/release ballistics; UI maps RMS −60…0 dBFS to 0…1.
- **Transmit voice clean-up (`MicProcessor`, added 2026-11-05 after the first on-air test sounded "mostly clear"):** G.711 does nothing to the signal (8 kHz sampling + log quantisation), and the first live test sent the raw mic at only −28 dBFS peak. Per 20 ms frame, after `MicGain` and before the VU meter/encoder (`NodeAudioEngineOptions.MicProcessing`, driven by the `MicProcessing` setting, default **on**, checkbox in Settings): (1) 2nd-order Butterworth **high-pass at 300 Hz**; (2) slow **AGC** towards −21 dBFS RMS (≈ −6 dBFS speech peaks): gain range −12…+24 dB, attack 0.5/frame, release 0.03/frame (~0.7 s), **gate at −50 dBFS** — pauses/noise never raise the gain and it drifts back to 0 dB (0.02/frame) so hiss is not left boosted; gain is ramped across each frame (no clicks); (3) **soft limiter** (tanh knee from 70% of a 0.89 FS ceiling) instead of hard clipping. Unit-tested (rumble −18 dB+, 1 kHz within 1.5 dB, quiet voice lifted to target, loud voice tamed under the ceiling, pauses not amplified, silence stays silence, ramped gain). **Owner reported good on-air voice quality on 2026-11-11.** A controlled A/B comparison is optional.
- **Receive gain, auto-level & Android extra speaker boost (`RxAudioProcessor`, 2026-11-22):** `RxAudioProcessor` applies manual receive gain (`RxGain`, 0.5×–4.0× slider, 0.25–8.0 validated; 1.0× without auto-level is a bit-exact pass-through), optional gated AGC (`RxAutoLevel`: target −15 dBFS RMS, −6…+18 dB gain, attack 0.55/frame, release 0.05/frame, −44 dBFS gate with 0.025/frame idle decay so pauses/hiss are not amplified), smooth frame-to-frame gain ramping, and a `tanh` soft limiter (`LimiterCeiling` 0.94, `LimiterKnee` 0.72). Runs in `NodeAudioEngine.PlayOneFrame` **after** `RxFrameDecoded` (so saved Audio Replay WAVs remain clean at unity gain) and **before** `OutputLevelChanged` / `EnqueuePlaybackPcm`, and also inside `AudioClipPlayer` using live `NodeRuntime.LiveRxGain`/`LiveRxAutoLevel` providers during replay. Both **RX** and **TX** (`NodeAudioEngine.MicGain` / `SanitizeMicGain`, `NodeRuntime.SetLiveMicGain`) sliders plus the **Auto** toggle live inside `PttCard` (`GainsGrid`) directly between `MetersGrid` and the shortened `PttRow` (`PttButton`/`SpeakerButton`), updating all active links immediately and debounce-saving atomically (`MainViewModel`). On Android, `RxLoudnessBoost` enables native `Android.Media.Audiofx.LoudnessEnhancer` (`+600` to `+1200 mB` scaled across `1×–4×` in `RxAudioProcessor.ComputeAndroidLoudnessMillibels`) attached to each active `AudioTrack` (`AndroidAudioDeviceService`, guarded in `try/catch` and released with the track). Unit- and headless-UI-tested (including Skia screenshots across phone/landscape/desktop layouts); **not yet heard on a physical Android phone**.
- **Voice timestamps (`Iax2Session.NextVoiceTimestamp`):** mini-frame timestamps used to be the wall clock at send time, which measured live as 16–24 ms spacing around a nominal 20. Now each voice frame is stamped previous + its own duration (20 ms), nudged ≤ 1 ms/frame towards the wall clock when it is > 5 ms away (so drift never accumulates), and restarted from the wall clock after a gap > 100 ms or at the start of an over. Unit-tested (jitter → 19–21 ms spacing, 1 % clock drift stays within 8 ms over 60 s, gap resync, 16-bit wrap).
- **Several links = several engines (2026-11-06).** Each `NodeLink` keeps its own `NodeAudioEngine` **and its own `IAudioDeviceService`** (the runtime calls the audio factory once per link); the OS mixes the outputs (WaveOut / AudioTrack / AVAudioEngine each play independently), so nothing in the verified single-link audio path changed. Only the transmit link ever opens the mic (it opens only while keyed), so there is still one capture. `NodeAudioEngine.Muted` silences one link: audio is still decoded, metered and reported via `RemoteAudioActiveChanged` (the row still shows "Receiving"), but nothing is enqueued to the device (zeros instead when `KeepAudioPipelineAlive`, so iOS keeps its session). **No cross-link repeating:** audio from one node is never forwarded to another (NodeX is an endpoint, not a hub). Android multi-link use is owner-reported; maximum-load mixing is not separately measured. iOS multiple engines remain unverified. Open speakers can increase echo.
- **Known behaviour:** all heads (desktop, Android, iOS) set `OpenMicOnlyWhileKeyed`, so the mic is open only while keyed (+3 s hold-off) — see §19–20. The input meter is idle while the mic is closed. Desktop enabled 2026-11-06; not yet heard/checked live (first words after keying may clip).
- **Echo (desktop):** there is no acoustic echo cancellation on desktop; with open speakers and a live mic the received audio will be re-transmitted. Use a headset. Mobile uses the platform's voice-communication processing (§7). Not yet addressed.

### 4.5 `NodeLink` and `NodeRuntime` (Core/Link)
- **`NodeLink`** = one call: `Iax2Session` + `NodePttController` + `NodeAudioEngine` + its device. Logs in as IAX user **`radio`** with `CALLING_NUMBER` = local node (see §5.4). Audio starts when the session reaches `Connected` (off the receive thread). `WasConnected` records whether it ever connected.
- **`NodeRuntime`** is the UI-toolkit-independent coordinator. API: `StartAsync`, `ApplyConfigAsync`, `ConnectAsync(targetNode)`, `DisconnectAsync`, `Link`, `Config`, registration state (`IsRegistered`, `RegistrationStatus`, `PerceivedAddress`), and events `RegistrationChanged`, `LinkChanged`, `LinkActiveChanged(bool,node)`, `ReconnectChanged(ReconnectStatus)`, `ErrorOccurred`, `Notice`. Saving settings (via `NodeConfigService.Changed`) re-applies configuration and (re)starts registration automatically.
- **`LinkActiveChanged`** means "a node link is *wanted*" — it stays `true` across automatic reconnects so platform heads don't tear down background services mid-recovery. Android uses it to start/stop the foreground service. With several nodes the node argument (and `BackgroundState.LinkedNode`) is a comma-joined list, e.g. "27339, 55553", so the notification reads "Linked to node 27339, 55553".
- **Multiple nodes at once (2026-11-06; design: Flowstep "NEW Multi-node links - phone").** `NodeRuntime` keeps one **`NodeConnection`** per wanted node (public read-only view: `Node`, `Info`, `Link`, `Reconnect`, `IsTransmitTarget`, `Muted`); each owns its own reconnect loop, early-hang-up counter and `Wanted` flag — the per-link logic of §4.6 is unchanged, just per node. API: `ConnectAsync(node)` **adds** a link (max `MaxLinks` = 8, raised from 4 on 2026-11-09, else `InvalidOperationException`); connecting to a node that is already linked redials just that node and keeps its transmit/mute choice; `DisconnectAsync()` hangs up all, `DisconnectAsync(node)` one; `Connections`, `Links` (live calls), `TransmitNode`, `SetTransmitNode(node?)`, `SetMuted(node, bool)`; events `LinkAdded`, `LinkRemoved`, `ConnectionsChanged` (any change: set, state, transmit, mute, reconnect). **`Link` still exists and means the transmit node's live call** (null when none/between attempts); `LinkChanged` was removed (replaced by `LinkAdded`/`LinkRemoved`); `Reconnect`/`ReconnectChanged` report the first node that is recovering (per node: `NodeConnection.Reconnect`).
  - **Transmit rules (safety):** exactly one link may key. The first node linked becomes the transmit node; later ones are listen-only until the user picks one (`SetTransmitNode`; an active key on the old node is released). If the user hangs up the transmit node and exactly one link remains, that one becomes the transmit node; **if the far end drops the transmit node, the choice is left empty** (notice "Node N ended. Choose a node to transmit to.") and PTT is inert until the user chooses — a transmission is never silently redirected to a different RF node. **A dial that fails (lookup failed, host not found, connect threw) counts as the far end, not the user (2026-11-21 review):** before, it took the "user hung up" path and armed the sole remaining node; now the choice is left empty. Test: `AFailedDial_DoesNotMoveTransmitToTheSurvivingNode`. A transmit node that is only reconnecting stays the transmit node. DTMF (keypad and macros) goes to the transmit node only.
  - **Network handoff** now re-dials every established link (each node recovers on its own loop); registration is refreshed once.
  - Errors from a link are prefixed "Node N: " when more than one node is linked.

### 4.6 Auto-reconnect and network handoff (spec of record)
**Auto-reconnect** (setting `AutoReconnect`, default on) re-dials when an **established** link is lost:

| Link ended because… | Re-dial? |
|---|---|
| Keep-alive watchdog / retransmit limit / INVAL (`LinkLost`) **and** the link had been `Connected` | **Yes**, with back-off |
| `LinkLost` (or busy) but the call was **never answered** | **Yes (2026-11-19, owner decision)**, normal back-off up to `MaxDelay`, until the user disconnects; notice "No response from node N … NodeX will keep trying until you disconnect it"; the cached address is dropped first. With `AutoReconnect` off: error "No response from node N" and stop. An explicit `REJECT` is still final. |
| Remote hung up **within `EarlyHangupWindow` (10 s; was 3 s until 2026-11-19, when a phone log showed hang-ups at 2.4 to 3.6 s) of ACCEPT**, and not after `!!DISCONNECT!!` (`RemoteHangup`, `NodeLink.ConnectedDuration` below the window) | **Yes**, back-off `InitialDelay`×`Factor`^(n−1) capped at `MaxDelay`, with **no limit** by default (`EarlyHangupMaxRetries` null, owner decision 2026-11-19; was 30 ≈ 28 min, and 10 before 2026-11-06); notice "Node N hung up straight after accepting; it probably doesn't know this node yet (a busy hub can take 10 minutes or more). Retrying in X s (retry n)"; only with a configured limit, the error "Node N keeps hanging up right after accepting the link…" and stop. Why: live-verified that an ASL3 node accepts, then app_rpt hangs up ~90 ms later ("Reported node N cannot be found") until its own node list has learned this node (minutes after registering or after an address change). Needs `AutoReconnect` on. The counter resets on a new user Connect and when a link stays up past the window. |
| Remote hung up later than that (`RemoteHangup`) **after sending `!!DISCONNECT!!`** (`Iax2Session.RemoteRequestedDisconnect`) | No — notice "Node N disconnected …: the far node ended the link on purpose" |
| Remote hung up later than that **without** `!!DISCONNECT!!` (its Asterisk restarted, or it gave up on packets we could not answer in a network gap shorter than our 45 s watchdog) | **Yes (2026-11-12)**, back-off `InitialDelay`×`Factor`^(n−1), with **no limit** by default (`RemoteHangupMaxRetries` null, owner decision 2026-11-19; was 5, app_rpt's own `MAX_RETRIES`); notice "Node N dropped the link … without asking to disconnect … Reconnecting in X s (try n)"; a link that stayed up `StableLinkTime` (5 min) starts a fresh count, as does a user Connect; only with a configured limit, the error "…has dropped the link n times in a row, so NodeX has stopped reconnecting" and the node is removed. Until 2026-11-12 this case was never redialled, which is how linked nodes "randomly" vanished (§5.6). |
| Remote rejected / busy | No — error. **Also during a reconnect (2026-11-21):** a retry answered with `REJECT` stops the loop with "Node N rejected the connection, so NodeX has stopped reconnecting." and removes the node (it used to be retried forever). A retry answered `BUSY` stays a never-answered retry. A REJECT/BUSY answer does not drop the cached address. |
| First dial: the node's address cannot be found (public: no directory/DNS/last-known result; private: host does not resolve) | **Yes (public since 2026-11-21, private since 2026-11-20)** while `AutoReconnect` is on: error "Cannot find node N. NodeX will keep trying until you disconnect it." and the node stays listed and retries. With it off: error and removed. |
| User pressed Disconnect | No (also cancels any reconnect cycle) |
| `AutoReconnect` off | No — error "Link to node N lost". **Turning it off while a node is retrying (2026-11-21)** stops that loop at once and removes the node (notice "Auto-reconnect is off, so NodeX stopped reconnecting to node N."); the loop also re-checks the setting before every dial. Live calls are untouched. |

Back-off (`ReconnectPolicy`): first retry after `InitialDelay` 2 s (immediately after a network change), ×`Factor` 2 per failure, capped at `MaxDelay` 60 s, each attempt must reach `Connected` within `AttemptTimeout` 12 s, `MaxAttempts` null (unlimited) by default. While there is no usable network the loop waits (re-checking every 5 s or on any network event) instead of burning attempts. Status is published as `ReconnectStatus(Active, Attempt, NextAttemptIn, Message)`.

**Rules added 2026-11-12 (after a phone log of six nodes all hanging up straight after accepting when Wi-Fi came and went within 9 s):**
- *A network change gives every node a fresh early-hangup budget.* Each new public address makes every far node hang up straight after accepting until it has learned that address, and a network event also cuts the back-off wait short, so a phone hopping between Wi-Fi and cellular spent the (then 30) retries far faster than the 28 minutes they were sized for. `HandleNetworkChangedAsync` zeroes `NodeConnection.EarlyHangups` on a real (signature) change.
- *A call's end is handled exactly once* (`NodeLink.EndHandled`). A link that dropped just as its reconnect loop finished was reported both by its state event and by the loop's last look, which could count two retries for one hang-up.
- *Every node that leaves the list logs why:* `[link] node N: no longer linked and will not be redialled: <reason>` (`RemoveConnection`). **Media commands never hang a node up (owner decision 2026-11-12):** in the Android car/media service (`NodeXMediaBrowserService`) a media **Pause or Stop** (car screen, steering wheel, headset or Bluetooth stereo) and a **permanent audio-focus loss** (another app took the audio) now **mute every linked node** and keep the links up; **Play** unmutes them (and re-requests audio focus). The mute is the driver's choice, so a later navigation prompt does not undo it. Before this they hung up the car's current node with nothing in the log, which looked like a link dropping by itself. Rules in Core `CarMediaButtons` (Pause/Stop → `Mute`, Play → `Unmute`; pinned by `AndroidServicePolicyTests`); the service side logs `[car] muting N node(s), none hung up: <why>`, `[car] unmuting …` and every `audio focus changed`. Hanging up from the car is still done with the per-node Disconnect / Disconnect all custom actions. Not tested on a car or phone.
**Superseded 2026-11-20: nothing mutes automatically (owner: "unless I press I really don't want anything muted").** Android Auto and Bluetooth stereos send Pause/Stop on their own (leaving the car, disconnecting), which left every node muted on the phone. Now media **Pause/Stop are ignored** (`CarMediaAction.Ignore`, logged as `[car] media Pause command ignored (nothing muted)` with Detailed logging), **Play only re-takes audio focus** (`CarMediaAction.Resume`, mute state untouched), and **audio-focus changes never mute** (navigation prompt, call or another app; Android ducks NodeX under prompts because of `SetWillPauseWhenDucked(false)`). Any media button and any focus loss still release a car transmission. The only ways to mute are the phone's per-node Mute button and the car's Mute custom action. **Consequence to watch:** during a phone call in the car, node audio is no longer silenced by NodeX; not tested on a car or phone.
**Hear nodes over the car radio (2026-11-20, setting `CarRadioMix`, off by default, both editions; Settings → "Android Auto: hear nodes over the car radio"):** a head unit plays one media source, so with the car's FM/AM/satellite radio (or another app) as its source NodeX's media audio is not heard; navigation prompts are mixed over it. Rules in Core `CarRadioMix` / `RadioDuckGate`: mixing **applies** when the option is on, the car is active (`CarSession.Active`) and NodeX does **not** hold the car's media audio (`CarSession.HasCarAudio`, set by `NodeXMediaBrowserService`: true when its media focus request is granted or regained, false on permanent focus loss or when the car session ends). Then the playback track uses `USAGE_ASSISTANCE_NAVIGATION_GUIDANCE` (`AndroidAudioDeviceService`, rebuilt on `CarSession.Changed`/`CarAudioChanged`), and `AndroidRadioDucker` (owned by `NodeForegroundService`, so it works without Android Auto showing NodeX) polls its own `RxActivity` every 100 ms and holds `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK` (navigation-guidance attributes) while any **unmuted** node is heard, releasing `ReleaseDelay` = 1.5 s after the last heard audio. When NodeX is the car's source it plays as media as before, and the ducker never requests focus then (so it cannot take focus from NodeX's own media session). Detailed log: `[car] radio mix: node talking, ducking the car audio (Granted)` / `radio mix: quiet, car audio back up`. Tests: `CarRadioMixTests`. **Unverified assumptions:** that switching the head unit to its own radio reaches the phone as a permanent focus loss (if it is transient, `HasCarAudio` stays true and mixing never starts); how each head unit renders navigation-stream audio (one speaker, fixed volume); whether Android Auto forwards navigation-stream audio between ducks. Not tried in a car.

**Network handoff:** `INetworkMonitor` (default `SystemNetworkMonitor`: `NetworkChange` + `NetworkInterface`) reports changes; events are **debounced 0.5 s** (1.5 s until 2026-11-06) and compared by *signature* (set of up, non-loopback, non-tunnel, non-link-local IPv4 addresses) so DHCP renewals are ignored. On a real change: (1) **re-register immediately** (so the registry/remote nodes learn the new address; waits up to 5 s), (2) if a link was established, end it and **re-dial immediately** from the new address (an IAX2 call is bound to the source address and cannot migrate), (3) if the network vanished, wait for it to return. Where the platform restricts network enumeration (recent Android) `SystemNetworkMonitor` degrades to "assume available, signature unknown" and the keep-alive watchdog still catches the loss (~45 s). Android uses `AndroidNetworkMonitor` (ConnectivityManager callback) instead.

**Requirement (owner, 2026-11-19): moving between Wi-Fi and cellular must be seamless.** A new network means a new public IP, and that IP has to reach the AllStarLink registry and then every far node before links are accepted again. The chain and who controls each step:
1. *Detect the change.* NodeX: local-address signature (above), plus the STUN check every 25 s on the call socket, which catches a carrier changing the **public** IP while the local (CGNAT, e.g. 10.x) address stays the same. Then it re-registers at once. The STUN check runs only while registered over IAX2, not on the HTTPS fallback.
2. *Tell the registry.* NodeX: re-registers immediately from the new call socket (IAX2), so the registry stores the address calls will come from (§5.1a). This takes seconds.
3. *Far nodes learn it.* **Not in NodeX's control.** Each far node checks callers against its own copy of the node list (ASL1/2: a downloaded file refreshed every few minutes; ASL3: DNS or file, per its config). Until then it accepts and hangs up within ~100 ms ("cannot be found") or logs "does not match link IP". The exact refresh interval per ASL version is **unverified**; field logs show "minutes", and a busy hub 10+.
4. *Re-link.* NodeX: re-dials every link at once, then retries early hang-ups with back-off capped at 60 s and no limit (§4.6, counts reset on each change), so a link returns within about a minute of the far node refreshing.

**Gaps against "seamless" (open, not built):**
- *Break-before-make.* Every link is hung up the moment the network changes, so there is no audio for the whole of step 3 (minutes). When the old path still works (cellular stays up while Wi-Fi joins), a **make-before-break** handoff would hide that gap: keep the old calls on a socket bound to the old network (Android `Network.bindSocket`), register and dial from the new network in parallel, and drop each old call only once its replacement is accepted. The catch: the registry keeps one IP per node, so registering the new address is what lets new calls in, while existing calls should survive because app_rpt checks the caller only at connect time (believed, **unverified**). Wi-Fi to cellular on leaving Wi-Fi range can't overlap like this, because the old path is already gone.
- *Public IP changes with no local change.* The STUN check re-registers, but linked calls are not re-dialled. They wait for the 45 s keep-alive watchdog. They should be re-dialled at once, as on a signature change.
- *HTTPS fallback.* With no STUN check, a public-IP change is picked up only by the next 60 s HTTPS registration.

### 4.9 Private and manually addressed nodes (specced & implemented 2026-11-20; unit + headless UI tested, live dial pending)
**Goal:** connect to a node that is not in the public AllStarLink directory (private node numbers such as 1000–1999, LAN/VPN nodes, club hubs on dynamic DNS) by giving its address by hand. Everything after address lookup (handshake §5.3, login as user `radio` §5.4, multi-node and transmit-node rules §4.5, retry until the user disconnects §4.6) is unchanged. The owner designs the UI; this section fixes behaviour and data only.

**What exists today:** `NodeResolution.SetStaticOverride(node, IPEndPoint)` is checked before the cache and the public lookups (§4.7), but nothing calls it, it is not saved, it takes an IP only, and it is keyed by node number alone.

**Address entry — one parser, `ManualNodeAddress.TryParse` (Core):** the Connect box and any "add private node" form accept:

| Input | Meaning |
|---|---|
| `1999` | public node: normal lookup (today's behaviour) |
| `1999@host` | node 1999 at `host`, port 4569 |
| `1999@host:4570` | as above, explicit port |
| `1999@[2001:db8::5]:4569` | IPv6 literal in brackets (parsed; dialling needs the IPv6 item in §13) |
| `radio@host:port/1999` and `radio@host:port/1999,NONE` (or `,<ip>`) | a line from a `[nodes]` stanza in rpt.conf, pasted as is; the `1999 =` prefix of a full stanza line is also accepted |

Rules: the node number is validated like any node number (3–7 digits). `host` is a DNS name or IPv4/IPv6 literal, trimmed and lower-cased. In the rpt.conf form the user part must be `radio` (anything else is shown as an error, not silently ignored) and the trailing `,NONE`/`,<ip>` is ignored. Spaces around `@`, `:` and `/` are tolerated. Anything else is a parse error with a message that names the expected forms. Tests: a table of good and bad inputs, including the four rpt.conf variants.

**Storage:** a new settings list `PrivateNodes` of `{ Node, Host, Port, Name? }` (default Port 4569). It lives beside `FavoriteNodes` and is validated and normalised the same way (duplicate (Node, Host, Port) entries removed). A private entry shows in the favourites list and in the car browse tree like a favourite, marked as private. Settings export (§4.7) includes the entries. An entry holds no secret.

**Resolution:**
- **Resolve the host on every dial.** The address is not cached for 15 minutes: club servers often sit on dynamic DNS, and the existing unanswered-dial rule (§4.7 `Invalidate`) then needs nothing extra. IPv4 is preferred, as for public nodes.
- **Use the given port exactly.** The public-node port probe with fallback to 4569 (§5 East Coast Reflector note) is **not** applied: the user typed the port.
- **Private addresses never go to AllStarLink services.** A private entry is never looked up via stats/REST/DNS on allstarlink.org, and the host is not sent anywhere except in the DNS query that resolves it.
- If the host cannot be resolved, the dial fails with "Cannot find host <host>" and is retried under the normal rules (§4.6), with no public lookup fallback.

**Identity and the one known limit:** a private node number is not unique (two clubs can both run 1999). The link's identity becomes (Node, Host, Port), so a private 1999 and a public 1999 (or two private ones) can be saved side by side. **First version:** `NodeRuntime` still keys links by node number, so linking two nodes with the same number **at the same time** is refused with a clear message ("Node 1999 is already linked via <host>"). Lifting that is a later change in `NodeRuntime`/`LinkItemViewModel`, not part of this item. Troubleshooting log lines in `DiagnosticLog` still record resolved endpoints, while **user-facing UI screens** (hero card, linked cards, top chips, favorites, Settings → Auto-connect, Private Nodes list/share header, activity log tags, and Android Auto browse) show only the node number/name and `PRIVATE` badge — the host is shown only on the Private Node creation/edit form (owner decision, 2026-11-21).

**Login:** always IAX user `radio`, no secret, exactly as §5.4. **Per-entry IAX usernames/secrets are deliberately not supported (owner decision 2026-11-20)**: a private server that requires its own IAX user and password cannot be linked. Our node password (registration) is still never sent to a remote node.

**Reachability hint:** when an entry is saved (and on demand), send one IAX POKE to the resolved address and show "reachable" / "no answer". This is information only: a silent POKE does not block saving or dialling (43136 ignored POKEs, §13 item 8).

**Sharing (optional, second step):** a link `nodex://add?node=1999&host=<host>&port=4569&name=<text>` (and the same as a QR code) opens a pre-filled "add private node" form. It never connects and never saves without the user confirming. Android: an intent filter; desktop: a protocol handler where the OS allows it. iOS is parked (§20).

**What NodeX cannot fix — must be explained in the UI/help:** the private server's app_rpt checks **our** calling node number against **its own** node list (§5.4). Unknown → instant hang-up ("Reported node N cannot be found"); wrong IP → "does not match link IP". If the private server downloads the public ASL node list and our node is registered, this works on its own after the list refresh. If the server is offline from ASL, firewalled or LAN-only, its admin must add us to `[nodes]` in rpt.conf, e.g. `<our node> = radio@<our public IP>:<port>/<our node>,NONE`. The help text offers a copy button for that line, filled with our node number and the address the registry last reported (`PerceivedAddress`/`PerceivedPort`, §4.7). The private server must also accept UDP 4569 (or its port) from us; NodeX only dials out and needs no inbound port.

## 5. ASL & IAX2 protocol requirements (verified facts)

### 5.1 HTTPS registration (verified against `AllStarLink/app_rpt` `res/res_rpt_http_registrations.c`)
- `POST https://register.allstarlink.org/` — **root path**, `Content-Type: application/json`.
- Body: `{"port":4569,"data":{"nodes":{"<node>":{"node":"<node>","passwd":"<password>","remote":0}}}}` — `node` is a JSON **string**; field is `passwd`; `port` omitted if 0; `remote` is the integer 0 for a real node.
- Reply JSON: `ipaddr` (public address the registry sees), `port`, `refresh` (seconds), `data` (status text). **Registered iff `data` contains "successfully registered".**
- Official client re-registers every **60 s**. Registration also keeps the node's public address current in the ASL registry/DNS, which is how remote nodes can validate us (§5.4).

### 5.1a Registering from the call socket (2026-11-19; field-proven need, updated 2026-11-22 after live protocol checks)
- **Why:** app_rpt (ASL1 `forward_node_lookup`, seen in the 41605 logs) drops an incoming link whose source **IP** differs from the IP in its downloaded node list: `Node N IP A does not match link IP B`. Only the IP is compared, not the port. On carrier NAT an HTTPS registration (TCP) and a UDP call can leave through different public addresses (Tom, node 41603, 5G: registered from 74.254.145.15, called from 74.254.149.17; and on 2026-11-22 with v1.29 on AT&T, STUN saw UDP `74.254.84.65:43193` / `:43194` consistently across Google and Cloudflare STUN servers while HTTPS fallback registered `74.254.78.54`). A node missing from the list gives `Reported node N cannot be found`.
- **How:** one `Iax2Endpoint` (UDP socket) carries every call and the IAX2 registration (`REGREQ` username = node number, `REFRESH` 60 → `REGAUTH` MD5 challenge → `REGREQ` with `MD5_RESULT` → `REGACK` with `APPARENT_ADDR` and `REFRESH`), so the registry records the socket's own public mapping. register.allstarlink.org still accepts IAX2 registration (41605 registers that way). `FallbackRegistration` uses HTTPS if IAX2 gets no reply twice or a rejection before it has ever worked, and tries one IAX2 registration every 5 min while on HTTPS, switching back when it is accepted; never both at once (HTTPS would overwrite the entry with the TCP path's address). The registrar listens on all of the registry's addresses (3 on 2026-11-19) and rotates re-sends through them. **Live-checked 2026-11-22** against all three `register.allstarlink.org` IPs (`52.44.147.201`, `52.20.63.146`, `52.21.169.197`): the registry answers `REGREQ` with `REGAUTH` (`OSeqno=0`, `ISeqno=0`, `AuthMethods=2`, `Challenge`), drops the pending transaction if an explicit `ACK` is sent before the authenticated `REGREQ` (causing a malformed `F=0` reply), expects the authenticated `REGREQ` with `OSeqno=1, ISeqno=1` (implicitly ACKing `REGAUTH` without `CallToken` when none was challenged), and returns `REGREJ` with `CauseCode=29` (no text `Cause` IE) for unknown credentials. **Full `REGACK` acceptance verified live on 2026-11-22** via `NodeX.LiveCheck register --iax` using node `523802`: `Registered (IAX2)` with `APPARENT_ADDR`, `refresh=60 s`, and `verdict=Consistent` matching both STUN servers.
- **Keeping the address stable:** a STUN request every 25 s keeps the mapping alive while idle-registered; a dial re-registers first if the last registration is older than 20 s; a network change opens a new socket and re-registers.
- **Limit:** a carrier that maps one socket to a different public IP per destination cannot be fixed on the phone. `NetworkCheck` detects it (two STUN servers disagree) and warns; only a relay or client-mode design would help (not built).

### 5.2 IAX2 frames (RFC 5456)
- Full frame header 12 bytes (F bit + 15-bit source call, R bit + 15-bit dest call, 32-bit timestamp, OSeqno, ISeqno, frame type, C bit + 7-bit subclass); mini frame 4 bytes (source call, 16-bit timestamp). Frame types: DTMF 1, Voice 2, Control 4, IAX 6, Text 7.
- **IAX subclasses (§8.4):** NEW 1, PING 2, PONG 3, ACK 4, HANGUP 5, REJECT 6, ACCEPT 7, AUTHREQ 8, AUTHREP 9, INVAL 0x0A, **LAGRQ 0x0B, LAGRP 0x0C**, REGREQ 0x0D, REGAUTH 0x0E, REGACK 0x0F, REGREJ 0x10, REGREL 0x11, VNAK 0x12, DPREQ 0x13, DPREP 0x14, DIAL 0x15, TXREQ 0x16, TXCNT 0x17, TXACC 0x18, TXREADY 0x19, TXREL 0x1A, TXREJ 0x1B, QUELCH 0x1C, UNQUELCH 0x1D, **POKE 0x1E**, MWI 0x20, UNSUPPORT 0x21, TRANSFER 0x22; **CALLTOKEN 0x28 is an Asterisk extension** (not in the RFC table; IE 54 / 0x36).
- **Control subclasses (§8.3):** Hangup 1, Ringing 3, **Answer 4, Busy 5**, Congestion 8, Flash 9, Option 0x0B, **Key Radio 0x0C, Unkey Radio 0x0D**, Call Progress 0x0E, Proceeding 0x0F, Hold 0x10, Unhold 0x11. (`AST_CONTROL_KEY`/`UNKEY` *are* the RFC's Key/Unkey Radio pair.)
- **Keep-alive:** `POKE` is only valid **outside** a call with destination call number 0 (§6.7.1). In-call liveness uses **PING/PONG** (§6.7.2; RFC default 20 s, NodeX uses 15 s for cellular-NAT headroom).
- **Codec:** µ-law (format bit 0x04) at 8 kHz, 20 ms = 160 bytes per frame.

### 5.3 Call handshake
`NEW`(+empty CALLTOKEN IE) → `CALLTOKEN`(token) → `NEW`(+token, fresh sequence space) → `ACCEPT` → we `ACK`. Then control/voice flow. Hang-up: `HANGUP` with a `CAUSE` IE.

### 5.4 How a node-to-node link logs in (from ASL `iax.conf` docs; **verified live against ASL3 node 523800**, see `docs/LIVE_VALIDATION.md`)
Incoming node connections land on the IAX user **`radio`** (`[radio]`: `type=user`, `context=radio-secure`, **no secret**); authentication happens afterwards in the `radio-secure` dialplan via `app_rpt`, which validates the calling node against the **remote node's own local node list** (refreshed from the registry/DNS on a delay of minutes — hence the importance of registration, and the early-hangup retry rule in §4.6). Therefore the link must use **Username `radio`**, `CALLING_NUMBER` = our node number, **no password**. The node **password is for registration only** and is never sent to remote nodes (a test asserts this). `[allstar-public]` (md5, secret `allstar`) and `[allstar-sys]` (RSA) are different, unused paths.

### 5.5 Keying and DTMF
PTT down → control `KEY` (0x0C) then voice; PTT up → stop voice, control `UNKEY` (0x0D). DTMF = full frame type 1 whose subclass is the ASCII digit. ASL function codes used: `*3<node>`, `*1<node>`, `*70`.

### 5.6 Deliberate disconnect vs dropped call (verified in the app_rpt source 2026-11-12; **not yet seen live**)
Read from `AllStarLink/app_rpt` `apps/app_rpt.c` (`remote_hangup_helper`, `handle_link_data`) and `apps/app_rpt/app_rpt.h`:
- A node that ends a link **on purpose** (operator unlink, a dialplan connection time limit) first sends the text frame **`!!DISCONNECT!!`** (`DISCSTR`; sent with its terminating NUL, `sizeof(DISCSTR)`), then hangs up. The receiving node stops its retries (`rpt_link_stop_retries`).
- A link whose far end hangs up **without** that text is treated as dropped: an outbound link that had connected is redialled, up to `MAX_RETRIES` = 5 (`MAX_RETRIES_PERM` for permanent links). No `!!DISCONNECT!!` is sent on an Asterisk shutdown or when the far side's own IAX2 retransmits time out.
- NodeX follows the same rule (§4.6): `Iax2Session.IsDisconnectText` matches the text exactly after trimming NUL/whitespace; full frames are processed in sequence order, so the text is always seen before the `HANGUP` that follows it.
- **Unverified:** that the nodes the owner links to (ASL3 and older app_rpt/HamVoIP builds) all send `!!DISCONNECT!!` on an operator unlink. If one does not, NodeX redials it up to 5 times after being unlinked on purpose, then stops.

## 10. Security & privacy requirements
- The node password lives **only** in `ISecretStore` and in memory; never in settings JSON, logs, status messages, UI error text, or any IAX packet (tests assert each of these).
- Registration is IAX2 over UDP by default with HTTPS as fallback (§5.1a); a configured HTTPS registration URL must be https (validator rejects others). IAX2 registration answers only an MD5 challenge: a `REGAUTH` without a challenge, or without MD5 in `AUTHMETHODS`, gets no answer (2026-11-21; it used to send MD5("" + password)). Registry rejection text has the password replaced by `***` before it is shown or logged.
- A link never answers an IAX2 `AUTHREQ` with the password itself: only the MD5 challenge method is used, and a request that could only be met in plaintext (no challenge, or no password, which is the normal case for a node link) ends the call as rejected (tested).
- Only the dialled endpoint may send to the call socket; spoofed/other-call packets are dropped (tested).
- No telemetry. The only outbound traffic: registry (IAX2/UDP or HTTPS), directory/DNS lookups (including 1.1.1.1/8.8.8.8 as DNS fallback), STUN to `stun.l.google.com` (every 25 s while registered over IAX2, NAT keep-alive) and `stun.cloudflare.com` (one-time network check), IAX2 to the linked node, and (full Android edition) GitHub release checks. `docs/PRIVACY.md` lists the same.
- Log redaction (`DiagnosticLog.Redact`) also covers JSON-style `"passwd":"..."` and `Authorization: Bearer ...` (2026-11-21).
- Settings Save starts from the loaded settings (`SettingsViewModel._loadedSettings with {...}`), so settings not on the form (e.g. `IaxRegistration`) are kept. `NodeConfigService.SaveAsync` restores the previous password if the settings write fails after the password was stored (a process kill between the two writes is still not covered).
- Saved audio replay clips (`<appData>/history/*.wav` + `index.json`) stay strictly on the local device (never uploaded or backed up to cloud); sharing a WAV clip requires an explicit tap by the user. Replay always plays through the local speaker and never keys or sends audio over IAX2.

**Rules for writing tests here:**
- Use `new TaskCompletionSource(TaskCreationOptions.RunContinuationsAsynchronously)` for anything signalled from a Core event; otherwise the test continuation runs *on the receive thread* and disposing the session from the test deadlocks.
- Wait on real state, not flags that flip early (e.g. wait for the *device* to be capturing; `NodeAudioEngine.IsRunning` becomes true before the device opens — this caused a flaky test).
- xUnit discovers only **public** test classes, so test methods can't take internal types as parameters (pass strings).

## 12. Engineering conventions & known pitfalls (for any agent)

- **.NET tooling only.** Do not use Python (or other languages) to edit/patch this repo; use normal edits and `dotnet` commands.
- **Do not edit generated or output files; do not put `bin`/`obj` in the repo** (§3.3).
- **CommunityToolkit.Mvvm generates `On<Property>Changed` partial hooks.** Naming your own method e.g. `OnSessionStateChanged` for a property `SessionState` causes a duplicate-member compile error — use `Handle…`.
- **Avalonia 12:** `TextBox.Watermark` is obsolete → `PlaceholderText`. `InputMethodOptions` attached property does not exist as I tried to use it. Use the palette brushes.
- **iOS project has no implicit usings** (add `using System;` etc.). The .NET iOS binding names differ from Apple's (`AllowBluetooth`, `AVAudioSessionMode.VoiceChat`).
- **Android:** the file-scoped namespace `NodeX.UI.Android` shadows the global `Android` root — write `global::Android.Manifest…` / `global::Android.Net.WifiMode` inside it; `Android.Media.AudioFormat` collides with `NodeX.Core.Audio.AudioFormat` (use an alias).
- **Event threading:** Core events fire on network/audio threads. UI code must marshal to the UI thread; Core code must not dispose a session/link from inside its own handlers (use `Task.Run`).
- **Core must stay UI-free.** New cross-platform behaviour goes in `NodeX.Core` behind an interface (`IAudioDeviceService`, `ISecretStore`, `INetworkMonitor`, `IBluetoothPttService`), implemented in the heads and unit-testable with fakes.
- **Nothing sensitive in logs/UI strings.** Never include the password in any message.
- **State your verification honestly** in commit messages/PRs: "unit-tested", "builds", "ran on device X".

## 18. Diagnostics

`DiagnosticLog` writes a rolling local `nodex.log` plus two older files (512 KB each). Passwords/tokens are redacted; node numbers and IPs can appear. Detailed logging is optional. Settings → Send logs opens Android's share sheet or the desktop file manager; nothing uploads automatically. **Shared text order (2026-11-19):** the share text (max 120,000 characters) starts with the newest ~20,000 characters under "MOST RECENT ENTRIES", then the older part under "OLDER ENTRIES" (`DiagnosticLog.ReadForSharing`, `AppServices.ShareRecentChars`): a log shared on 2026-11-19 was cut off at the end by the receiving app and so lacked the day it was sent for. **Registration lines to look for:** `[reg] registration starting over ...`, `IAX2 registration did not work on this network (...)`, `IAX2 registration works again`, `registration lapsed`, and `[net] network check ... verdict=...`.

**"A node disappeared" (2026-11-12):** search the log for `no longer linked and will not be redialled` (the reason follows), `[car] muting` / `[car] unmuting` and `audio focus changed`. A pasted excerpt is not enough when it starts after the event: ask for the whole file from Send logs.

The receive highlight rule lives in Core `RxActivity` and is shared by the phone UI and car service. KEY-aware nodes follow KEY/UNKEY; non-KEY-aware nodes use a 2000 ms voice hold (`RxActivity.VoiceHold`, raised from 500 ms on 2026-11-22 after a field report of green RX blinking during mid-speech pauses; receiving an `UNKEY` clears `LastSoundTicks` immediately so hubs that only send `UNKEY` still drop right when the over ends). A KEY without subsequent frames expires after 3 seconds. A lost UNKEY while a KEY-aware peer continues streaming remains an open limitation.
**False-RX hardening (2026-11-20, after an owner report of occasional false RX; cause not pinned down from the log):** (1) the voice-hold window for non-KEY nodes (`RxActivity.VoiceHold`, 2000 ms) counts only frames with sound in them (`RxActivity.HasSound`: decoded µ-law RMS above `SoundRmsDbfs` = `-40 dBFS`), so a hub streaming silent idle frames or low background noise no longer lights; silent frames still keep a KEY alive through pauses (`LastVoiceTicks` vs `LastSoundTicks`), and `UNKEY` clears `LastSoundTicks` at once. Root causes addressed: (1) `AndroidAudioDeviceService` now opens `AudioTrack`s lazily on first written audio and releases them after 15 s of idle silence (so silent linked nodes do not hold 7 idle `PLAYING` clients against `AudioFlinger`), requests `AudioTrackPerformanceMode.LowLatency` (with fallback to `None`), verifies `AudioTrackState.Initialized`, caps API 31+ `SetStartThresholdInFrames` to 40 ms so deep-buffer `USAGE_MEDIA` tracks never stall above `MaxDeviceBacklog` (200 ms), logs `[audio]` track lifecycle/route events, and uses `PlaybackStallDetector` to rebuild tracks asynchronously on negative/zero writes or frozen `PlaybackHeadPosition`; (2) `AndroidAudioRoute` now fires `RouteChanged` after `SetCommunicationDevice`; (3) `NodeForegroundService` applies `DefaultToSpeaker` on first link before `StartBluetoothSco` and calls `StopBluetoothSco()` when `BluetoothSco` is false; (4) `MainViewModel.OnLinkActiveChanged` applies `DefaultToSpeaker` only on the `false -> true` transition and ignores stale queued `false` transitions. Unit-tested (`PlaybackStallDetectorTests`) and Android builds with 0 warnings/errors; **live phone re-test pending.**

## 19. Desktop audio and Bluetooth

- Windows audio uses NAudio; Linux/macOS use PortAudio. Saved input/output names are resolved on each new link, with a logged fallback when a device is unplugged. Linux needs JACK/ALSA dependencies; a native-load failure falls back to silent audio.
- A small linux-arm64 harness ran on the owner's Raspberry Pi. It verified native loading, device listing, capture/playback opening and sample cadence. The Pi had no microphone and no listening check was performed. The full Avalonia app, real audio and keyring behavior still need Linux/macOS testing.
- `tools/package-macos.sh` builds a `.app` with microphone/Bluetooth usage descriptions. Packaging is implemented but has not been run on a Mac; signing/notarization is not automated.
- Desktop BLE uses `DesktopBlePttTransport` and `SimpleBleCentral` (SimpleSharpBLE 1.4.0). Supported native builds: Windows 10+ and glibc Linux, x64/ARM64; macOS 15+ on Apple Silicon. Intel Macs and older macOS do not have BLE support from this package. Linux needs BlueZ/D-Bus and permission to access the Bluetooth service. Native access is deferred until Scan/connect, so an absent adapter does not prevent ordinary operation.
- Scan reports paired and advertising devices; connection subscribes to available notification/indication characteristics. The existing Learn wizard records the exact button packets. Connecting/scanning/learning never keys; disconnect releases a held button and old-connection notifications are ignored. Native Windows adapter enumeration and scan/start/stop passed on the development PC. Real-button behavior remains unverified. See `THIRD_PARTY_NOTICES.md` for the separate BLE dependency license.
